## Problem Statement

Backend and CLI bugs are still shared as prose, screenshots, logs, and incomplete reproduction steps. BugProof should make a bug feel like a runnable fixture: one command captures the failure, one artifact travels with the issue, and one replay proves whether the same failure happens again.

For an open source side project, the first version should optimize for a developer seeing the demo and immediately understanding the magic. The goal is not to solve every portability problem up front. The goal is to make a same-machine or same-project replay feel trustworthy, inspectable, and useful.

## What Makes This Cool

The "whoa" moment is turning an annoying bug report into a `.bug` artifact that behaves like a tiny executable case file. A maintainer should be able to run:

```bash
bugproof replay auth-timeout.bug
```

and see a crisp result:

```text
Replaying: python app.py --tenant acme
Expected: TimeoutError: auth service did not respond
Actual:   TimeoutError: auth service did not respond
Result:   reproduction confirmed
```

The personality layer matters: replay should compare the captured failure to the current failure, explain mismatches, and point at likely missing context such as secrets, files, runtime versions, or dependency gaps.

## Constraints

- Start as a local CLI, not a hosted service.
- Target backend and CLI programs first, not browser UI sessions.
- Support same-OS/same-project replay first; cross-OS portability can wait.
- Never store secrets. Capture their presence as schema requirements only.
- Keep artifacts inspectable. A `.bug` should be a directory or archive with plain JSON and copied files, not an opaque binary blob.
- Avoid deep deterministic debugging in the first version. BugProof is not `rr`, GDB, Docker, or a VM.

## Premises

- The fastest path to delight is not perfect portability; it is reliable replay of a captured failure in a familiar development environment.
- The artifact format is the product. If developers can inspect and trust the artifact, they are more likely to share it.
- A polished replay diff can make a simple capture system feel dramatically more useful.
- Open source adoption depends on a tiny first workflow: capture a real failure, replay it, and understand the result without reading a long manual.

## Approaches Considered

### Approach A: Proof Capsule CLI

Build the smallest `.bug` artifact that captures command, working directory metadata, selected files, sanitized environment schema, stdout/stderr, exit code, runtime hints, and a failure fingerprint. Replay restores the captured context enough to rerun the command and compare the new failure to the original.

This approach is the best foundation because it creates the core artifact and the core loop. It also keeps the project honest: if capture and replay are not compelling, integrations will only decorate a weak center.

### Approach B: GitHub Issue Repro Bot

Build a workflow that creates or updates a GitHub issue with a `.bug` artifact and replay instructions. This would make the demo more social and visible, especially for open source maintainers.

This is exciting, but it depends on the artifact being useful first. Without a working proof capsule, the issue integration becomes another bug-reporting wrapper.

### Approach C: Replay Diff Experience

Focus on the replay output: expected vs actual failure, missing environment hints, dependency mismatch hints, file drift warnings, and a clear reproduction verdict.

This is the strongest delight layer, but it should ride on top of the proof capsule rather than replacing it. The first version should include enough of this to make the demo memorable.

## Recommended Approach

Choose Approach A with the strongest pieces of Approach C.

The first design target is a Proof Capsule CLI: a minimal artifact format plus capture/replay commands. The replay output should still feel polished from day one. It should not merely rerun a command; it should answer the question maintainers care about: "Did this reproduce the same bug, and if not, what context is probably missing?"

## Open Questions

- Should the first artifact be a directory by default, an archive by default, or support both?
- How strict should file capture be: explicit file allowlist only, automatic project snapshot, or a hybrid?
- Which runtime gets the first golden path: Python CLI, Node CLI, or any command with best-effort capture?
- How should BugProof fingerprint failures without becoming too language-specific?
- Should replay execute in-place, in a temp directory, or both?

## Success Criteria

- A developer can run `bugproof capture -- <command>` against a failing CLI command and get a `.bug` artifact.
- A second command, `bugproof replay <artifact>`, reruns the captured command and compares exit code, stderr/stdout signature, and failure fingerprint.
- Secrets are never written into the artifact. Required secrets appear in `env.schema.json`.
- The artifact is inspectable with ordinary tools and contains a clear `manifest.json`.
- The first demo can reproduce at least three real local bug cases: missing dependency, missing environment variable, and deterministic runtime exception.
- Replay output includes a verdict: confirmed, mismatch, or blocked by missing context.

## Distribution Plan

Start with npm because the repo is already TypeScript/Node and the target user is comfortable with CLI tools:

```bash
npm install -g bugproof
```

During early development, support local usage through:

```bash
npm run cli -- capture -- <command>
npm run cli -- replay <artifact>
```

Publishing can wait until the proof capsule is useful locally. The initial distribution path is README-driven open source usage, then npm once capture/replay has stable behavior and a few fixtures.

## Next Steps

1. Define the `.bug` artifact structure:
   - `manifest.json`
   - `env.schema.json`
   - `files/`
   - `failure.json`
   - `metadata.json`
   - `run.json` or `run.sh` depending on platform strategy

2. Implement `bugproof capture -- <command>`:
   - Run the command.
   - Capture exit code, stdout, stderr, duration, cwd, command args, and sanitized environment metadata.
   - Copy selected files into the artifact.
   - Write a basic failure fingerprint.

3. Implement `bugproof replay <artifact>`:
   - Validate required environment variables.
   - Restore files into a temp workspace.
   - Rerun the command.
   - Compare actual output to captured failure data.

4. Build the replay verdict:
   - `confirmed` when the exit code and failure fingerprint match.
   - `mismatch` when the command fails differently.
   - `blocked` when secrets, files, or runtime assumptions are missing.

5. Add three fixture bugs:
   - Missing dependency.
   - Missing required environment variable.
   - Deterministic thrown exception.

6. Polish the README around one tight demo:
   - "Capture this failing command."
   - "Replay the generated artifact."
   - "See reproduction confirmed."
